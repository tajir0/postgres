# 行缓存在热点读多写少场景下的验证报告

> 写行缓存主要改动：
> 内存分配由动态分配改成了预分配的固定共享内存和 1MB 段控制容量，并通过后台 washer计算段的衰减LFU分数和淘汰冷段、补空闲段。
> UPDATE/DELETE立即失效,按旧主键从哈希桶摘除缓存项。UPDATE 后的新版本不会立即写入缓存。事务回滚也不恢复旧缓存项，只造成后续 miss，不影响正确性。INSERT 不直接写缓存.
> 点查 miss 时在原生 Index Scan 返回真实行后按需回填。

## 1. 关键数据

### 1.1 PostgreSQL 关键参数


| 参数                       | 值          |
| ------------------------ | ---------- |
| `row_cache_size`         | 10240MB    |
| `row_cache_hash_buckets` | 16,777,216 |
| `shared_buffers`         | 30G        |


`row_cache_size` 只表示缓存数据段池大小。16,777,216 个桶头在 64 位系统上

还会单独占用约 128MB 实例级共享内存。

| 参数         | 值    |

| `duration` | 100s |

## 2. 测试数据

测试为 BenchmarkSQL 的 `public.bmsql_stock` 表，100仓TPC-C`public.bmsql_stock` 表的数据量为1000万行。

## 3. 工作负载设计

### 3.1 均匀读写

每个 pgbench 事务只执行一条 SQL，读和更新的脚本权重为10:1：

读取语句：

```sql

\set wid random(1, 10)

\set iid random(1, 100000)

SELECT s_quantity, s_data FROM bmsql_stock WHERE s_w_id = :wid AND s_i_id = :iid;


```

更新语句：

```sql

\set wid random(1, 10)

\set iid random(1, 100000)

UPDATE bmsql_stock SET s_ytd = s_ytd + 1 WHERE s_w_id = :wid AND s_i_id = :iid;


```

### 3.2 热点行读写

热点模型为：

```text

80% 请求访问每个仓库 1，000，000个 item

20% 请求访问每个仓库其余 9，000,000 个 item


```

即 80% 请求集中于 10% 行，但热点集合仍包含 100 万行，避免客户端集中

更新少数行而使测试退化成行锁串行测试。读取和更新访问少数热点行，能够真实触发“缓存命中、更新失效、读取回填”的循环。

读取语句：

```sql

\set wid random(1, 10)

\set r random_zipfian(1, 100000, 1.01)

\set iid 1+permute(:r - 1, 100000)

SELECT s_quantity, s_data FROM bmsql_stock WHERE s_w_id = :wid AND s_i_id = :iid;

```

更新语句：

```sql

\set wid random(1, 10)

\set r random_zipfian(1, 100000, 1.01)

\set iid 1+permute(:r - 1, 100000)

UPDATE bmsql_stock SET s_ytd = s_ytd + 1 WHERE s_w_id = :wid AND s_i_id = :iid;
```

random_zipfian(1, 100000, 1.01)是中等偏重的长尾分布，permute(:r, N)把热行**随机散布**在 `[1,100000]` 全域——热行不再聚堆,分散在不同页上。

## 5. 最终结论

1. **行缓存能够提升主键点查性能。** 在本次测试环境中，纯读场景 TPS 提升约 **12.1%～17.2%** ；加入约 10% 更新后，均匀读写场景仍有 **5.9%～10.6%** 的提升，说明行缓存对读多写少负载具有稳定的正向收益。
2. **写入会降低行缓存的相对收益。** UPDATE 本身不能通过行缓存加速，并会摘除旧缓存项、增加失效处理开销。因此，相比纯读场景，混合读写场景的总体收益有所下降。当前方案更适合读取占主导、主键点查频繁的业务，而不是写密集型负载。
3. **回填策略具有明显的负载相关性。** 均匀访问场景中，开启回填的 TPS 比关闭回填低约 0.5%～3.2%，表明回填产生的元组复制、段内分配和哈希插入成本超过了其命中收益；热点场景中，开启回填比关闭回填高约 2.1%～5.6%，说明被更新失效的热点行能够通过后续读取重新进入缓存，维持热点集合的命中率。
4. **并发升高后，相对收益整体趋于下降，但不随并发单调下降。** 热点混合读写场景的提升由 10 客户端时的 9.5% 降至 60 客户端时的 2.5%。高并发下瓶颈从"单次查询的索引下探成本"转移到全局共享资源竞争(缓存分区锁、cache line竞争、CPU 调度)，缓存节省的下探占比被稀释。在并发增加到100～300后（测试机器上的逻辑线程数是60），基线TPS持续下降，表明系统已经进入CPU过载、上下文切换和共享资源竞争加剧的饱和区间，此时三个场景下TPS相对基线都有一定回升。这表明系统过载后，原生索引与堆表访问路径的退化速度更快，而行缓存由于缩短了执行路径、减少了页面访问等开销，表现出更好的过载韧性，但100～300并发数据主要反映系统过载时的性能保持能力，而不是正常容量范围内的线性扩展能力。
5. **综合来看，当前“失效 + 按需回填”方案是可行的。** 它能够在不改变 PostgreSQL 事务语义的前提下，为热点读多写少场景提供正收益；但回填不应无条件开启。对于热点集中、失效后会被重复访问的负载，建议开启回填；对于访问分散的负载，可以关闭回填，仅保留初始装载和 DML 失效。
